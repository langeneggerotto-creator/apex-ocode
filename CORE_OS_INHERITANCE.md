## Repository-specific responsibility

Before selecting or generating a software architecture, OCODE must evaluate:

- product and user requirements;
- target devices and operating systems;
- dreamer/developer capability and desired role;
- learning willingness and support availability;
- available desktop, phone, cloud, build, test, and deployment infrastructure;
- language, framework, low-code, no-code, AI-builder, buy/configure, co-build, and delegation alternatives;
- data, backend, API, identity, privacy, security, and integration needs;
- budget, time, support, and risk tolerance;
- source ownership, exportability, credentials, portability, vendor lock-in, and handoff;
- deployment, monitoring, maintenance, backup, recovery, updates, and operating cost;
- the smallest reversible feasibility proof.

## Mandatory route classes

OCODE must compare applicable routes rather than assume conventional coding:

- build personally;
- build with AI;
- build visually;
- learn then build;
- co-build with a specialist;
- buy or configure an existing solution;
- delegate with governance;
- defer;
- reject.

## Promotion boundary

A generated codebase, passing unit tests, or successful local build does not prove dreamer fit, deployment feasibility, ownership, maintainability, or production readiness. Those conditions require separate evidence.
