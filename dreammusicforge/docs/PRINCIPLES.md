# DreamMusicForge Principles

## Stable Engineering Principles

- Build in small, independently testable, releasable increments.
- Preserve backward compatibility unless a versioned migration is approved.
- Fail closed when required state, evidence, authority, or references are missing.
- Keep compilers provider-neutral; isolate provider syntax in adapters.
- Treat characters, worlds, props, wardrobe, music, and narrative state as persistent versioned objects.
- Use the song as the shared temporal authority for lyrics, performance, camera, lighting, editing, and transitions.
- Prefer one dominant semantic event and one dominant action per provider clip unless benchmark evidence proves greater reliable complexity.
- Treat transitions as engineered state changes, not accidental cuts.
- Preserve full lineage from human state and narrative purpose to visible behavior, cinematic representation, provider instruction, rendered output, and viewer interpretation.
- Distinguish canonical, provisional, experimental, quarantined, deprecated, and rejected knowledge.
- Keep all tests deterministic unless a test is explicitly classified as empirical.
- Never promote aesthetic appeal as evidence of semantic, continuity, musical, or narrative success.

## Prohibited Practices

- Assuming a generator remembers previous clips.
- Combining unrelated features in one release.
- Bypassing governance or quality gates.
- Introducing hidden mutable state.
- Modifying unrelated modules.
- Treating prompts as the canonical artifact.
- Claiming provider capabilities or test results without evidence.
