## Truth boundary

Canonical documentation defines project intent and requirements but does not, by its presence alone, prove that every described capability is implemented.

Implementation, provider dispatch/generation, character identity, semantic lip-sync, singing/lyric correctness, continuity quality, final creative quality, CI status, and release status must each be independently evidenced before being claimed as verified.

## Development discipline

Preserve verified increments in GitHub with evidence, tests where applicable, truth boundaries, version history, and rollback points. Prefer small independently testable releases over monolithic changes.
